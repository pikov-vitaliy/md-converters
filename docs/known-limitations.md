# Известные ограничения (не баги) и окружение

Перенесено из CLAUDE.md 2026-08-29 при его сокращении. Каждый пункт
здесь — СОЗНАТЕЛЬНОЕ решение с обоснованием; прежде чем «чинить»,
прочитай его целиком. Новые ограничения дописываются сюда.

## Окружение


- Python, на который указывают команды:
  `C:\Users\user\AppData\Local\Programs\Python\Python314\python.exe`.
  На машине есть и второй Python (`...\Local\Python\pythoncore-3.14-64\`) —
  install.ps1 выбрал первый (он на PATH).
  **ВАЖНО (проверено 2026-08-04 по хэшам файлов).** Живой код
  (`V:\md-converters\*.py` + `gui_static/`) исполняют только два пути:
  функции профиля `tomd`/`pdf2md`/`html2md` (они зовут скрипт по
  ПОЛНОМУ пути) и `.venv` проекта (редактируемая установка). А
  `tomd.exe`/`tomd-gui.exe`, которые резолвятся из PATH (они из
  `pythoncore-3.14-64\Scripts`), запускают СТАРЫЕ КОПИИ из
  site-packages — у обоих системных Python свои копии, обе отстают от
  репозитория. Отсюда следствия: `tomd-gui` (профильной функции для
  него нет) поднимает устаревший GUI; в cmd.exe, где функции профиля
  не работают, устаревшим оказывается и `tomd`. Актуальный GUI —
  `V:\md-converters\.venv\Scripts\tomd-gui.exe`. Чтобы PATH-команды
  перестали расходиться, нужна редактируемая установка:
  `<python> -m pip install -e "V:\md-converters[gui]"`. Зависимость:
  `markitdown[pdf,docx,pptx,xlsx,xls,outlook]` ≥ 0.1, < 1.0 (потолок —
  чтобы мажорный релиз не прилетел молча). НЕ `[all]`: его
  `youtube-transcript-api` требует Python < 3.14, и pip на 3.14 молча
  откатывается на древний markitdown 0.0.2 (без CSV-таблиц и т.п.).
  Плюс `pdfplumber` (≥0.11.9,<1.0.0), `pypdfium2` (≥4,<6) и
  `requests` (≥2.32,<3) объявлены ПРЯМЫМИ зависимостями — они
  импортируются напрямую (pdfplumber/pypdfium2 — PDF-таблицы и подсчёт
  страниц; `requests` — загрузка URL в `convert_url` под SSRF-контролем),
  хотя приходят и транзитивно через `markitdown`; явное объявление
  страхует от смены состава зависимостей под потолком `markitdown<1.0`.
  Все — MIT/BSD/Apache-2.0, без AGPL.
- ОС: Windows 11. Оболочка: PowerShell 7 (pwsh). `$PROFILE` — для текущего
  хоста (PowerShell 7).

## Известные ограничения (не баги)

- **PDF-таблицы — извлекаются через pdfplumber по геометрии** (линии/края
  заливок), а НЕ штатным путём MarkItDown (тот ищет таблицы по координатам
  слов и слипает/рвёт колонки). См. функции `_pdf_tables_result`,
  `_page_blocks`, `_segment_table_rows`, `_join_continued_tables`,
  `_table_to_gfm` в `convert_to_md.py`. Есть фильтр «это таблица» (отсекает
  прозу), обрезка/переэмит прилипшей прозы, склейка переносных таблиц по
  повтору заголовка, отброс пустых колонок, сборка текста и таблиц по
  порядку чтения без дублирования. Поле `pdf_tables: N` во front-matter.
  Отключение — `--pdf-tables off`. Предел метода: полностью «голые»
  таблицы без линий/фона и сканы (нет геометрии) — там best-effort, нужен
  ML-извлекатель (Docling и т.п. — отвергнут как обязательная зависимость:
  torch/вес/риск на Python 3.14). PyMuPDF/pymupdf4llm не берём — AGPL.
  Обоснование выбора и обзор кандидатов — в `docs/pdf-tables-proposal.md`.
- **Псевдографика таблиц (box-drawing `│┌┬┐├┼┤└┴┘─`) -> GFM.** Такие
  «таблицы» нарисованы символами рамок прямо в тексте (часто — генераторы/
  ИИ), геометрии у них нет, и в Markdown-вьюере они разъезжаются. `tidy()`
  (`_convert_box_tables`/`_box_block_to_gfm`) конвертирует их в GFM:
  двухстрочные шапки сливаются, внешние рамки срезаются. Работает для
  любого формата; триггерится только при наличии вертикалей `│`/`┃` (на
  прозу и на готовый GFM с ASCII `|` не влияет).
- **Абзацы и перечисления из PDF (`_merge_text_blocks`).** Блоки
  страницы склеиваются в `parts` через `\n\n`, но проза из табличных
  регионов приходит ПОСТРОЧНО (блок на строку), поэтому каждая строка
  PDF становилась отдельным абзацем Markdown: на реальном
  60-страничном документе 212 из 308 абзацев были однострочными, 140
  обрывались посреди предложения, медиана — 5 слов. Соседние
  текстовые блоки теперь склеиваются в один абзац (мягкие переносы),
  таблицы остаются границами. Исключение — пункты перечислений
  (`_LIST_ITEM_RE`: «и) …», «1) …», «– …»): мягкий перенос Markdown
  схлопывается в пробел, и склейка слила бы пункты в сплошную строку,
  поэтому пункт начинает новый абзац, а перенос ВНУТРИ пункта
  остаётся мягким. Правило применяется и к строкам внутри блока
  (`_split_list_items`) — иначе полоса `_crop_text` вела бы себя
  иначе, чем построчные блоки. Содержимое не меняется: на реальном
  документе мультимножество слов до и после ИДЕНТИЧНО. Побочно
  склейка сделала заметнее разрыв слова между строками (`(наприм` +
  `ер,`): раньше это были два абзаца, теперь — «наприм ер» внутри
  строки. Замер по словарю документа (`_clean_word_vocabulary`):
  таких разрывов РОВНО ОДИН на 60 страниц, и он же — единственная
  строка-огрызок; причина — тот самый разрыв ячейки между
  страницами (см. «Известный edge» ниже). Эвристика «склеить, если
  обе половинки не слова, а их сумма — слово» ОТКЛОНЕНА: ради
  одного вхождения она внесла бы риск молчаливого сращивания слов.
- **Чистка PDF-текста (`_clean_pdf_text` в `_pdf_tables_result`).** На
  многостраничных PDF (≥3 стр.) убираются сквозные колонтитулы
  (короткие строки — номер документа, версия) и страничные номера.
  Порог повторов колонтитула —
  `max(5, page_count // 2)`, то есть НЕ МЕНЬШЕ пяти при любом объёме:
  на 3-4-страничных PDF колонтитул с каждой страницы остаётся
  (сознательный консерватизм — на коротком документе легко срезать
  легитимный повтор). Номера страниц режутся ДВУМЯ независимыми
  путями: (1) старый — если найден сквозной колонтитул; (2)
  `_paginated_number_indices` — если голые числа образуют
  СОГЛАСОВАННУЮ сквозную нумерацию (строго возрастают по ходу
  документа, не превышают числа страниц, их набирается не меньше
  половины объёма И цепочка покрывает не меньше `_PAGE_NUM_SPAN`
  = 60% строк документа). Условие охвата добавлено не «на всякий
  случай»: без него нумерованный перечень (колонка «№» таблицы,
  разобранной как проза) сам проходил проверку длины и вырезался
  ЦЕЛИКОМ — на синтетическом 60-страничном документе молча исчезали
  все 40 номеров подряд. Отличает их именно охват: сквозная
  нумерация идёт через весь документ (замер на реальном PDF — 99%
  строк), перечень сидит в одном месте. Второй путь добавлен потому,
  что документ без
  повторяющегося колонтитула, но с нумерацией, оставлял её целиком в
  тексте: на реальном 60-страничном документе в `.md` висели 66 голых
  чисел. Число, выпадающее из цепочки, сохраняется — так уцелевают
  маркеры сносок и ссылки на пункты, а год на титуле («2026») спасает
  граница «не больше числа страниц». Плюс
  экранируются ложные ATX-заголовки: в PDF нет настоящих `#`-заголовков,
  поэтому `# ...` (комментарий конфига и т.п.) рендерился бы как H1 —
  экранируем в `\#`. Строки таблиц (`|`) не трогаются. Уникальные
  документы без повторов не страдают: одиночное число не режется ни
  одним из путей (закреплено тестом
  `test_clean_pdf_text_keeps_unique_doc_and_standalone_number`).
- **Фенсинг кода/команд/конфигов (`_fence_code_blocks`/`_classify_code_line`
  в `_clean_pdf_text`).** Прогоны строк-кода (команды, SQL, конфиги, вывод)
  оборачиваются в ``` — иначе `<плейсхолдеры>` съедаются рендером как HTML,
  `#`-комменты становятся заголовками, `|-vda` ломается как таблица.
  Классификатор построчный: русская проза кириллице-доминантна → проза;
  код — латиница-доминантная строка / команда (sudo, CLI `cmd -flag`) / SQL
  (CREATE/SELECT/MAC…) / `$VAR` / `{<...>}` / `UUID=`/`deb ` / продолжение
  `\`. Настоящие таблицы (`| … |`) и псевдографику (`│`) не трогаем (они —
  границы блока). `#`-экранирование делается только ВНЕ фенсов. Порог
  настроен на 0 ложных срабатываний на корпусе из 10 реальных документов
  Astra (3371 код-фенс, прозы во фенсах нет). Код построчно перемешан с
  прозой, поэтому фенсы часто короткие — это норма.
- **Только стратегия `lines` для таблиц** (`_PDF_TABLE_STRATEGIES`).
  Стратегия `text` (кластеризация слов) убрана: на плотном коде/SQL и
  многоколоночной прозе она порождала фейковые мега-«таблицы» (76x7) и
  крошила текст в огрызки. Настоящие таблицы разлинованы/с заливкой → их
  берёт `lines` (через края прямоугольников).
- **Известный edge:** строка таблицы, разорванная между страницами ПОСРЕДИ
  ячейки (метка на одной стр., значение — на следующей, плюс повтор
  заголовка), реконструируется не полностью (часть строк выходит прозой).
  Сегментация по строкам-склейкам нужна, чтобы РАЗДЕЛЯТЬ слипшиеся таблицы
  (одна страница), и это конфликтует с СОХРАНЕНИЕМ разорванной строки —
  выбран безопасный дефолт (разделять). Пример: хвост «Приложение B» в
  тестовом документе (строки «Статья»/«Финал»). Всё равно сильно лучше
  штатного MarkItDown.
- **Сломанная кириллица в PDF — ДВЕ карты шрифта, выбор построчный**
  (`_repair_broken_cyrillic_pdf_text`). Основной текст: строчные
  `0x30..0x4F` со смещением B0, прописные — управляющие `0x14..0x1F` со
  смещением AC. Сноски: строчные `0x34..0x53` со смещением AC,
  прописные `0x10..0x1F` со смещением B0. НЕ сводить к одной карте:
  чужая карта не «недоремонтирует», а превращает текст в другую
  бессмыслицу. Концевые `:`/`;` — пунктуация, а не буквы `к`/`л`
  (214 случаев на один документ), `<`/`>`/`@` — наоборот буквы;
  спорные случаи разрешает словарь самого документа
  (`_clean_word_vocabulary`). Знак `?` намеренно не в
  `_TRAIL_PUNCT`. Проходов ремонта ДВА: словарь второго прохода
  собирается по результату первого, иначе прогон без единой уцелевшей
  русской буквы остаётся без подтверждения. Прописные, закодированные
  управляющими символами, доходят до ремонта целыми (проверено:
  `extract_text()` их СОХРАНЯЕТ, 36 шт. на документ) — не путать с
  `tidy()`, который чистит управляющие символы уже ПОСЛЕ ремонта.
- **Word-таблицы:** MarkItDown даёт пустую верхнюю строку-заголовок, реальные
  заголовки уезжают в первую строку тела (данные не теряются).
- **Картинки:** base64 по умолчанию сворачиваются в плейсхолдер (решение
  пользователя — так и оставить).
- **PPTX-картинки:** MarkItDown не извлекает файлы картинок из `.pptx` —
  пишет битую ссылку `![alt](ИмяФигуры.jpg)` (а при пустых именах фигур,
  напр. из R7-Office, вырожденную `![](.jpg)`); просмотрщики Markdown
  рисуют вместо неё ошибку `EntryNotFound`/`ENOENT`. `tidy()` сворачивает
  такие ссылки в плейсхолдер (`_PHANTOM_IMG`, только для `.pptx`).
- **Управляющие символы:** перенос строки внутри абзаца PowerPoint
  (`<a:br/>`) python-pptx отдаёт как vertical tab `\x0b` — в `.md` это
  «квадратик». `tidy()` чистит: `_CTRL_TO_SPACE` (разделители строк →
  пробел) и `_CTRL_DROP` (C0/DEL/soft hyphen/ZWSP/BOM — удалить).

- **Ремонт кириллицы не включается на OCR-сканах (гейт 3%).** Скан
  ГОСТ Р 34.11-2012 проходил прежний порог плотности 1% впритык
  (1.01%), и ремонт молча портил hex-константы: «345» внутри хэша
  декодировалось в «где», которое словарь документа ложно
  подтверждал. Порог поднят до 3% (настоящий сломанный шрифт даёт
  ≥7% даже на коротких фрагментах, реальный документ — 11.5%), а
  чисто цифровые прогоны не переводятся вовсе — симметрично
  alt-ветке. Замер: 4 реальных PDF + 13 тестовых синтетик, разрыв
  минимум 2.2x в обе стороны.
- **17 токенов «*ентр(а)» ×10, «,ифр» ×5, «*елое» ×2 в документе
  ФСТЭК — принятый остаток.** Прописные Ц/Ш в пунктуационных слотах
  ОСНОВНОГО шрифта ('*'=0x2A→Ц, ','=0x2C→Ш при +0xAC). Частотный
  арбитр пункта 20 улик не имеет: сломанных хвостов больше, чем
  целых слов («ентра» ×10 против «центра» ×1, «шифр» ×3 против
  «ифр» ×14, «целое» ×0), а перевод без улик превращал бы настоящие
  '*'/',' (маркеры сносок, перечисления) в буквы. Видимо сломанный
  токен честнее невидимой порчи.
- **Фолбэк MarkItDown (PDF без геометрических таблиц): чистится
  только колонтитул/номера страниц.** Фенсинг кода и экранирование
  заголовков настроены на pdfplumber-текст и на фолбэк не
  переносятся. Фейковые «таблицы» из разрежённого титула
  («| Н А Ц И | О Н А Л Ь |…» у Р 71207-2024) — продукт самого
  MarkItDown, не вычищаются.
- **IPYNB: выводы выполнения ячеек (outputs, включая stdout) в .md
  не попадают** — предел MarkItDown 0.1.6 (проверено на голом
  `MarkItDown().convert()`), авторские ячейки (markdown + code)
  доходят полностью.
- **JSON/XML конвертируются в сырой не-фенсированный текст** —
  многострочный JSON в Markdown-вьюере схлопнется в абзац. Потери
  нет, дефект косметический; фенсинг реализован только для PDF-пути.
