# CLAUDE.md — контекст проекта для AI-агентов

Этот файл — онбординг для Claude Code и любых AI-агентов. Прочитай его
первым, чтобы сразу быть в контексте проекта. Язык проекта — русский
(интерфейс утилит, README, комментарии). Пользователь: Виталий Пиков
(vitaliy@pikov.com), сфера — DevSecOps / безопасность; конвертирует
отчёты инструментов (SBOM, уязвимости, ГОСТ/РБПО-аудит) в Markdown для
базы знаний.

## Что это

**md-converters** — утилита перевода документов в Markdown на базе
[MarkItDown](https://github.com/microsoft/markitdown) (Microsoft). Одна
команда `tomd` определяет формат по расширению и конвертирует: PDF, HTML,
Word (`.docx`), Excel (`.xlsx`), PowerPoint (`.pptx`), CSV, JSON, XML,
EPUB, Outlook `.msg`, Jupyter, RSS и веб-страницы по URL.

## Архитектура

- **`convert_to_md.py`** — единственный скрипт, вся логика. Раньше было два
  отдельных (`convert_pdf_to_md.py`, `convert_html_to_md.py`) — они УДАЛЕНЫ
  и слиты сюда.
- Команды-обёртки: `tomd` = весь функционал; `pdf2md` = `tomd --only pdf`;
  `html2md` = `tomd --only html,htm`. Различие только в фильтре формата при
  обходе папки/маски (одиночный явный файл конвертируется всегда).
- Точки входа для pip (console_scripts в `pyproject.toml`):
  `cli_tomd` / `cli_pdf` / `cli_html` в `convert_to_md.py`.
- Поле `generator` во front-matter выводится из набора расширений
  (`_tool_name`): `{.pdf}`→`pdf2md`, `{.html,.htm}`→`html2md`, иначе `tomd`.

## Возможности / флаги

`-r` рекурсия (пропускает `node_modules/.git/.next/dist/build/venv/...`);
`-f`/`--force` перезапись (иначе существующие `.md` пропускаются);
`-o DIR` вывод в одну папку; совпадения имён `.md` всегда (и без `-o`)
разводятся суффиксами `(2), (3)...` со сверкой `source:` во front-matter
уже лежащих на диске файлов;
`--only EXT[,EXT]` фильтр форматов при маске/папке;
`--pdf-tables auto|off` (по умолчанию `auto`) — извлечение таблиц из PDF
по геометрии через pdfplumber; `off` — штатный текстовый путь MarkItDown;
`--keep-images` оставить base64-картинки (по умолчанию сворачиваются в
плейсхолдер `![...]()`); `--no-frontmatter` без YAML-шапки;
URL (`http(s)://`) — тянет страницу через `convert_url`.
Прочее: маски, папки, front-matter (title/source/converted/generator),
чистка вывода (`tidy`), сводка с перечнем ошибок, автоопределение кодировки
HTML (cp1251 и др.) через перекодировку во временный UTF-8.

## Известные ограничения (не баги)

- **PDF-таблицы — извлекаются через pdfplumber по геометрии** (линии/края
  заливок), а НЕ штатным путём MarkItDown (тот ищет таблицы по координатам
  слов и слипает/рвёт колонки). См. функции `_pdf_tables_result`,
  `_page_blocks`, `_segment_table_rows`, `_join_continued_tables`,
  `_table_to_gfm` в `convert_to_md.py`. Есть фильтр «это таблица» (отсекает
  прозу), обрезка/переэмит прилипшей прозы, склейка переносных таблиц по
  повтору заголовка, отброс пустых колонок, сборка текста и таблиц по
  порядку чтения без дублирования. Поле `pdf_tables: N` во front-matter.
  Отключение — `--pdf-tables off`. Предел метода: полностью «голые»
  таблицы без линий/фона и сканы (нет геометрии) — там best-effort, нужен
  ML-извлекатель (Docling и т.п. — отвергнут как обязательная зависимость:
  torch/вес/риск на Python 3.14). PyMuPDF/pymupdf4llm не берём — AGPL.
  Обоснование выбора и обзор кандидатов — в `docs/pdf-tables-proposal.md`.
- **Псевдографика таблиц (box-drawing `│┌┬┐├┼┤└┴┘─`) -> GFM.** Такие
  «таблицы» нарисованы символами рамок прямо в тексте (часто — генераторы/
  ИИ), геометрии у них нет, и в Markdown-вьюере они разъезжаются. `tidy()`
  (`_convert_box_tables`/`_box_block_to_gfm`) конвертирует их в GFM:
  двухстрочные шапки сливаются, внешние рамки срезаются. Работает для
  любого формата; триггерится только при наличии вертикалей `│`/`┃` (на
  прозу и на готовый GFM с ASCII `|` не влияет).
- **Чистка PDF-текста (`_clean_pdf_text` в `_pdf_tables_result`).** На
  многостраничных PDF (≥3 стр.) убираются сквозные колонтитулы
  (короткие строки — номер документа, версия) и страничные номера
  (только если колонтитул найден). Порог повторов —
  `max(5, page_count // 2)`, то есть НЕ МЕНЬШЕ пяти при любом объёме:
  на 3-4-страничных PDF колонтитул с каждой страницы остаётся
  (сознательный консерватизм — на коротком документе легко срезать
  легитимный повтор). Плюс
  экранируются ложные ATX-заголовки: в PDF нет настоящих `#`-заголовков,
  поэтому `# ...` (комментарий конфига и т.п.) рендерился бы как H1 —
  экранируем в `\#`. Строки таблиц (`|`) не трогаются. Уникальные
  документы без повторов не страдают (одиночное число не режется, если
  колонтитул не обнаружен).
- **Фенсинг кода/команд/конфигов (`_fence_code_blocks`/`_classify_code_line`
  в `_clean_pdf_text`).** Прогоны строк-кода (команды, SQL, конфиги, вывод)
  оборачиваются в ``` — иначе `<плейсхолдеры>` съедаются рендером как HTML,
  `#`-комменты становятся заголовками, `|-vda` ломается как таблица.
  Классификатор построчный: русская проза кириллице-доминантна → проза;
  код — латиница-доминантная строка / команда (sudo, CLI `cmd -flag`) / SQL
  (CREATE/SELECT/MAC…) / `$VAR` / `{<...>}` / `UUID=`/`deb ` / продолжение
  `\`. Настоящие таблицы (`| … |`) и псевдографику (`│`) не трогаем (они —
  границы блока). `#`-экранирование делается только ВНЕ фенсов. Порог
  настроен на 0 ложных срабатываний на корпусе из 10 реальных документов
  Astra (3371 код-фенс, прозы во фенсах нет). Код построчно перемешан с
  прозой, поэтому фенсы часто короткие — это норма.
- **Только стратегия `lines` для таблиц** (`_PDF_TABLE_STRATEGIES`).
  Стратегия `text` (кластеризация слов) убрана: на плотном коде/SQL и
  многоколоночной прозе она порождала фейковые мега-«таблицы» (76x7) и
  крошила текст в огрызки. Настоящие таблицы разлинованы/с заливкой → их
  берёт `lines` (через края прямоугольников).
- **Известный edge:** строка таблицы, разорванная между страницами ПОСРЕДИ
  ячейки (метка на одной стр., значение — на следующей, плюс повтор
  заголовка), реконструируется не полностью (часть строк выходит прозой).
  Сегментация по строкам-склейкам нужна, чтобы РАЗДЕЛЯТЬ слипшиеся таблицы
  (одна страница), и это конфликтует с СОХРАНЕНИЕМ разорванной строки —
  выбран безопасный дефолт (разделять). Пример: хвост «Приложение B» в
  тестовом документе (строки «Статья»/«Финал»). Всё равно сильно лучше
  штатного MarkItDown.
- **Сломанная кириллица в PDF — ДВЕ карты шрифта, выбор построчный**
  (`_repair_broken_cyrillic_pdf_text`). Основной текст: строчные
  `0x30..0x4F` со смещением B0, прописные — управляющие `0x14..0x1F` со
  смещением AC. Сноски: строчные `0x34..0x53` со смещением AC,
  прописные `0x10..0x1F` со смещением B0. НЕ сводить к одной карте:
  чужая карта не «недоремонтирует», а превращает текст в другую
  бессмыслицу. Концевые `:`/`;` — пунктуация, а не буквы `к`/`л`
  (214 случаев на один документ), `<`/`>`/`@` — наоборот буквы;
  спорные случаи разрешает словарь самого документа
  (`_clean_word_vocabulary`). Знак `?` намеренно не в
  `_TRAIL_PUNCT`. Проходов ремонта ДВА: словарь второго прохода
  собирается по результату первого, иначе прогон без единой уцелевшей
  русской буквы остаётся без подтверждения. Прописные, закодированные
  управляющими символами, доходят до ремонта целыми (проверено:
  `extract_text()` их СОХРАНЯЕТ, 36 шт. на документ) — не путать с
  `tidy()`, который чистит управляющие символы уже ПОСЛЕ ремонта.
- **Word-таблицы:** MarkItDown даёт пустую верхнюю строку-заголовок, реальные
  заголовки уезжают в первую строку тела (данные не теряются).
- **Картинки:** base64 по умолчанию сворачиваются в плейсхолдер (решение
  пользователя — так и оставить).
- **PPTX-картинки:** MarkItDown не извлекает файлы картинок из `.pptx` —
  пишет битую ссылку `![alt](ИмяФигуры.jpg)` (а при пустых именах фигур,
  напр. из R7-Office, вырожденную `![](.jpg)`); просмотрщики Markdown
  рисуют вместо неё ошибку `EntryNotFound`/`ENOENT`. `tidy()` сворачивает
  такие ссылки в плейсхолдер (`_PHANTOM_IMG`, только для `.pptx`).
- **Управляющие символы:** перенос строки внутри абзаца PowerPoint
  (`<a:br/>`) python-pptx отдаёт как vertical tab `\x0b` — в `.md` это
  «квадратик». `tidy()` чистит: `_CTRL_TO_SPACE` (разделители строк →
  пробел) и `_CTRL_DROP` (C0/DEL/soft hyphen/ZWSP/BOM — удалить).

## Подводные камни для агентов

- **Кириллица в имени `.lnk`:** `WScript.Shell.CreateShortcut` теряет
  кириллицу в ИМЕНИ файла (downconvert в ANSI → `?` → невалидное имя).
  Обход в install.ps1: создать ярлык с латинским именем, затем
  `Move-Item`/`Rename-Item` в кириллицу (это Unicode). Не «чини» обратно.
- **Длина строк в `convert_to_md.py`:** держи ≤ 79 символов — IDE-линтер
  ругается E501. Проверяй после правок.
- **`.ps1` без BOM:** дочерний `pwsh -File` читает как UTF-8 — кириллица ок;
  но профиль пишем с `utf8BOM`, чтобы читали и PowerShell 5.1, и 7.
- **Песочница** периодически блокирует `Remove-Item` с маской `\*` или
  подозрительными путями — используй `-LiteralPath` на конкретную папку.

## Как разрабатывать и проверять

1. Правки — в `V:\md-converters\convert_to_md.py` (и обёртки/README).
2. Проверка: компиляция `python -m py_compile convert_to_md.py`; длина строк
   ≤ 79; функциональный тест на реальных файлах во временной папке
   (`$env:TEMP`), результат смотреть, temp убирать.
3. Установщик идемпотентен — `install.ps1` можно гонять повторно (сам
   убирает старый блок профиля и пункт Send To, прописывает заново).
4. CI (GitHub Actions) на каждый push в `main` гоняет ruff-линт и
   смоук-тесты (HTML, CSV, пропуск без `--force`, ошибки флагов) на
   ubuntu (Python 3.10/3.11/3.12/3.13/3.14) и windows (3.12/3.14) —
   должен быть зелёным.

   **CI активен; репозиторий публичный.** 2026-06-16 репозиторий
   сделан публичным (`gh repo edit --visibility public`), потому что
   на приватном репо Actions тратят платные минуты, а платёж/лимит
   тогда исчерпался — CI падал мгновенно с «recent account payments
   have failed» и спамил «CI: All jobs have failed» на каждый push.
   На публичном репо стандартные раннеры бесплатны без лимита, биллинг
   больше не помеха. Если когда-нибудь понадобится пауза без оплаты —
   `gh workflow disable CI` (→ `disabled_manually`), вернуть —
   `gh workflow enable CI`.
   Локально тот же набор, что и в CI (голый `python` на PATH —
   заглушка Microsoft Store, поэтому через `uv`):
   `uv lock --check && uv sync --frozen && uv run --frozen ruff check
   convert_to_md.py tests tools && uv run --frozen pytest -q`.

    `:`/`;` (214 шт.) — всегда пунктуация, `<`/`>`/`@` (24 шт.) —
    всегда буквы `м`/`о`/`р`. Арбитр на случай слов вроде «материал»:
    если буква достраивает слово, встречающееся в документе целым
    (`_clean_word_vocabulary`), она сохраняется. `?` намеренно НЕ
    трогаем: слова на «п» («тип», «принцип») реальны, а `?` как
    пунктуация в этом жанре почти не встречается. (в) **Прогоны без
    уцелевшей кириллицы** (`<>45;L=>3>` → «модельного») раньше
    отбрасывались целиком — теперь переводятся, если результат
    подтверждён словарём документа. На 60 страницах это даёт ровно
    1 попадание и 0 ложных (`8601:2004`, `09:30:00`, `САО:`, `ЭКО:`
    остаются нетронутыми). Итог на реальном документе: 215
    исправленных строк, 0 регрессий. Все 5 новых тестов проверены на
    ОТКАТЕ соответствующей ветки кода — один сначала не краснел
    (строка из одних дат уходила в альт-ветку) и был переписан.
    172 pytest-теста (+12).

    **Остаточные дефекты (приняты).** `П>4@>1=>5` («Подробное»)
    словарём не подтверждается — 1 строка (см. пункт 19: после
    двухпроходного словаря это единственный остаток на документ).

19. **Двухпроходный словарь ремонта PDF (2026-08-29).** Проверка
    остатков пункта 18 дала две находки. **(а) Ограничение про
    управляющие символы было сформулировано СЛИШКОМ ШИРОКО** (правка
    от 2026-08-29, см. пункт 20: первая версия этого подпункта
    объявляла его целиком ложным — это была передозировка поправки, и
    её пришлось откатить по замеру). Точная картина такова.
    pdfplumber управляющие символы в основном СОХРАНЯЕТ: 36 шт.
    доживают до ремонта, и все 35 строк чинятся верно («ГОСТ Р»,
    «Защита информации», «СКЗИ»), а вычищает их `tidy()` уже ПОСЛЕ
    ремонта — так что «выбрасывает до нашего кода» как общее правило
    неверно. НО в двух конкретных позициях теряет, и это ровно те
    примеры, что стояли в исходном тексте: `\x1f` (буква «П») в начале
    строки отбрасывается вместе с номером сноски (`11 \x1fD< BJ9A>9`
    → `D< BJ9A>9`), отчего остаётся „ри“ вместо „При“; `\x1e` (буква
    «О») в середине строки превращается в пробел, отчего остаётся
    `Г !"` вместо „ГОСТ Р“. В обоих случаях pypdfium2 символ
    сохраняет, и ремонт отрабатывает (тест
    `test_repair_alternate_font_footnote_lines` подаёт именно
    pypdfium2-форму и даёт «При оценке»). Вывод для будущего: это
    ограничение ИЗВЛЕКАТЕЛЯ, а не ремонта. **(б) Реальный дефект:
    словарь строился только по сырому
    тексту.** Прогон без единой уцелевшей русской буквы переводится
    лишь при подтверждении словарём, но слова, которые в документе
    встречаются ТОЛЬКО сломанными, в сыром словаре отсутствуют по
    определению. Теперь ремонт делает два прохода: словарь второго
    собирается по результату первого (1001 → 2213 слов на реальном
    документе), перевод всегда заново из ОРИГИНАЛА. Последнее —
    защитный инвариант (карта заведомо не применяется дважды), а НЕ
    оптимизация: замерено, что цепочка «второй проход по результату
    первого» даёт на реальном документе идентичный вывод (0 различий).
    Не переписывать на цепочку: инвариант дешёвый, а гарантия его
    ценнее. **Почему именно два прохода:** замерено, что словарь
    насыщается за один раунд (1001 → 2219, следующий раунд +0), и
    третий проход даёт побайтово тот же вывод — два прохода это
    неподвижная точка, а не произвольное число. Не превращать в
    неограниченный цикл: каждый лишний раунд только расширяет шлюз и
    добавляет риск петли обратной связи (ошибочный ремонт → ошибочное
    слово в словаре → новые ошибочные ремонты). Проверено также
    `repair(repair(x)) == repair(x)`. Замер на реальном документе:
    второй проход принимает РОВНО два прогона, оба верных
    (`<>4C;59` → «модулей»,
    `О1J5<` → «Объем» — заголовок таблицы), ложных срабатываний 0;
    полный диff вывода — те же две строки, 0 регрессий. Отвергнуто:
    (1) нечёткое сравнение по общей основе — на реальном документе
    давало 0 ложных, но добирало лишь «модулей», который двухпроходный
    словарь берёт ТОЧНЫМ совпадением, то есть безопаснее; (2)
    структурное правило «одна заглавная кириллица + 4+ сломанных
    символа = слово», которое закрыло бы последний остаток
    («Подробное»): оно переводит БЕЗ словарного подтверждения и на
    других документах превратило бы обозначения вроде «С2000» в
    правдоподобную бессмыслицу. Видимо сломанный токен честнее
    невидимой порчи — тот же принцип, из-за которого концевая
    пунктуация была главной находкой пункта 18. Граница шлюза закрыта
    тестом `test_repair_keeps_technical_designations_intact`: при
    снятии словарной проверки он краснеет ровно предсказанной порчей
    («С2000» → «Свааа», «8601:2004» → «ижабкваад»). Проверено, что
    улик для «Подробное» в документе нет вообще: слово встречается
    один раз и только сломанным, оглавления с ним нет.
    174 pytest-теста (+2, оба проверены красным на реальном коде).

20. **Заглавные второго шрифта, спрятанные в пунктуации
    (2026-08-29).** Широкий аудит выхода (не только на кириллицу, но
    и на таблицы, фенсы, заголовки, переносы) нашёл то, что три
    прошлых прохода пропустили: 7 строк РУССКОЙ ПРОЗЫ внутри
    код-фенсов. Оказалось, это не ошибка фенсинга, а его СЛЕДСТВИЕ —
    прозу зафенсило потому, что она осталась недоремонтированной и
    полна пунктуации (`Г !"`, `Ф!"ЭК оссии`, `« азработка`).
    **Причина.** У второго шрифта прописные Р..Я лежат не в
    управляющих, а в ПЕЧАТНЫХ `0x20..0x2F` со смещением B0: «Р» — это
    пробел, «С» — `!`, «Т» — `"`, «Я» — `/`. Слепой перевод погубил бы
    все настоящие пробелы, а «С/С++» превратил бы в «СЯСЫЫ», поэтому
    их не трогали вовсе. **Решение — тот же принцип улики, что и в
    пункте 19, но арбитр другой: частота.** Для слова: пробел перед
    ним был буквой, если слово С заглавной встречается в документе
    ЧАЩЕ, чем без неё («азработка» 1 против «разработка» 4, «оссии» 1
    против «россии» 15). Обычное слово после настоящего пробела так не
    проходит: «Рбезопасного» в документе 0 раз. Для аббревиатуры
    арбитр прежний, словарный: `Ф!"ЭК` → «ФСТЭК», потому что «ФСТЭК»
    в документе есть целым. Из карты исключены «ъ», «ы», «ь» (русское
    слово с них не начинается), заодно из набора уходят частые `*`,
    `+`, `,`. Правило применяется ТОЛЬКО к строкам второго шрифта (8
    из 2197). **Тонкость, которую нельзя упрощать:** пробел-буква
    поглощает и разделитель слов, поэтому после буквы/цифры
    разделитель возвращается («ФСТЭК России»), а после кавычки — нет
    (««Разработка»). Обе ветки закреплены тестом. Замер на реальном
    документе: принято 3 восстановления (2 слова + 1 аббревиатура),
    все верные, ложных 0; полный диff итогового `.md` — ровно 2
    строки. Граница закреплена тестом
    `test_repair_keeps_real_punctuation_in_alt_font`, проверенным
    красным при снятии обоих шлюзов. **Остаток и его точная
    причина.** `Г !"` («ГОСТ Р») не чинится не из-за правила, а
    потому что `pdfplumber.extract_text()` сплющивает `\x1e` (это «О»)
    в пробел — без «О» аббревиатура словарём не подтверждается.
    Замерено: на тексте pypdfium2, где `\x1e` сохраняется, ТО ЖЕ
    правило даёт «ГОСТ». Смена извлекателя отвергнута сознательно:
    ради одного вхождения она затронула бы таблицы, порядок чтения,
    чистку колонтитулов и фенсинг разом. По той же причине остаются
    „ри“/„од“ вместо «При»/«Под»: pdfplumber отбрасывает ведущий
    `\x1f` («П») вместе с номером сноски, декодировать нечего
    (замер и разбор — в пункте 19(а), там же исправлена прежняя
    слишком широкая формулировка про управляющие символы).
    Также осознанно не чинятся
    однобуквенные слова (`4 также` → «а также», `6 предыдущих` → «в
    предыдущих»): одиночный символ неотличим от настоящей цифры.
    176 pytest-тестов (+2).
